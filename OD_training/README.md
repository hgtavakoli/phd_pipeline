# AAS-Driven YOLO Object Detection Pipeline

This repository provides an automated pipeline for training and evaluating YOLOv12 object detection models. The entire workflow is configured via a single Asset Administration Shell (AAS) file, creating a highly structured, reproducible, and standardized approach to managing complex deep learning experiments.

## Core Concept
The fundamental principle of this project is to use a single AAS JSON file as the "single source of truth" for all experimental parameters. Instead of manually editing multiple configuration scripts or remembering command-line arguments, a user defines everything—from dataset paths to training hyperparameters—within the structured AAS file.

The main Python script (`main.py`) orchestrates the entire workflow:

1.  **Parse AAS**: It reads the specified AAS file.
2.  **Generate Config**: It dynamically creates a `config.yaml` file that the underlying training scripts will use.
3.  **Launch Pipeline**: It runs the requested mode (`train` or `evaluate`) using this generated configuration.

This approach eliminates manual configuration errors and makes it trivial to track, version control, and replicate experimental setups.

## ✨ Key Features
*   **Centralized Configuration**: All parameters (paths, hyperparameters, model choices) are managed in one AAS JSON file.
*   **Automated Workflow**: The pipeline automatically generates YAML configs from the AAS before each run.
*   **Dual Modes**: Supports both `train` and `evaluate` modes for a complete workflow.
*   **Experiment Iteration**: Designed to loop through different datasets or camera angles defined in the AAS, training a separate model for each.
*   **Multi-GPU Support**: Ready for distributed training on both Linux and Windows (experimental) systems.
*   **Periodic Evaluation**: Automatically evaluates model checkpoints on a test set at a specified frequency during training and logs results to a unified CSV file.

## 🔧 Configuration: The AAS File
All experiment parameters are controlled from a single file: `AAS/CA_Modul-OD_pipeline_v0.5.json`. Open this file and modify the `value` fields as needed. The `idShort` keys correspond to the parameters used by the pipeline.

### Key Configuration Parameters (`idShort`)

| Path in AAS (ObjectDetection...) | Description | Example Value                                        |
| :--- | :--- |:-----------------------------------------------------|
| **Paths** | |                                                      |
| `paths.base_data_dir` | Absolute path to the root directory containing your training data subfolders. | `"C:/datasets/yolo_experiments/SINGLE_Class_Medium"` |
| `paths.val_data_path` | Absolute path to the validation dataset. | `"C:/datasets/yolo_val"`                             |
| `paths.test_data_path` | Absolute path to the test dataset used for periodic and final evaluation. | `"C:/datasets/yolo_test"`                            |
| **Training Hyperparameters** | |                                                      |
| `training.weights` | Pre-trained model file name (must be in the project root). | `"yolov12l.pt"`                                      |
| `training.epochs` | Total number of training epochs. | `200`                                                |
| `training.batch_size` | Images per batch. Adjust based on your GPU memory. | `16`                                                 |
| `training.img_size` | Image size (pixels) for training and evaluation. | `640`                                                |
| `training.save_period` | Save a model checkpoint every N epochs. Set to -1 to disable. | `10`                                                 |
| **Experiment Control** | |                                                      |
| `training.exp_names_to_train`| The base name for the experiment runs. | `"yolo_experiments"`                                 |
| `training.cameras_to_train` | Comma-separated list of training data subfolders to iterate over. | `"camera1,camera2,camera3"`                          |
| **Classes** | |                                                      |
| `classes.names` | Comma-separated list of your object class names in the correct order. | `"ClassA,ClassB,ClassC"`                             |

## ▶️ How to Run the Pipeline
The pipeline is launched via `main.py` and has two primary modes: `train` and `evaluate`.

### Local Execution (Windows & Linux)

**Single GPU Training (Recommended)**

For single-GPU training, use the standard `python` command. This is the most reliable method, especially on Windows.

**Important**: Always run this command in a new terminal to ensure no leftover environment variables from previous multi-GPU attempts interfere.
```bash
# Replace with the actual path to your AAS file
python main.py --mode train --aas_file "AAS/CA_Modul-OD_pipeline_v0.5.json"
```

**Multi-GPU Training**

To leverage multiple GPUs, you must use the `torchrun` launcher. It correctly initializes the distributed environment required for training.

*On Linux (Stable):*
```bash
# Use --nproc_per_node to specify the number of GPUs (e.g., 2)
torchrun --nproc_per_node=2 main.py --mode train --aas_file "AAS/CA_Modul-OD_pipeline_v0.5.json"
```

*On Windows (Experimental):*
Windows requires an extra flag to specify a compatible communication backend.
```dos
torchrun --nproc_per_node=2 --rdzv-backend=c10d main.py --mode train --aas_file "AAS/CA_Modul-OD_pipeline_v0.5.json"
```

### Evaluation
To evaluate all the `.pt` models generated during a training run, use the `evaluate` mode.
```bash
python main.py --mode evaluate --aas_file "AAS/CA_Modul-OD_pipeline_v0.5.json"
```

### HPC / Slurm Execution
For large-scale jobs, the pipeline can be run inside a container on an HPC cluster using Slurm.

1.  **Prepare the Container**: Ensure your Singularity/Docker container image includes all dependencies from `requirements.txt`.
2.  **Run with srun**: Use a command similar to the one below, updating paths to your project and container image.

```bash
python main.py --mode evaluate
```

## 📂 Understanding the Results
All outputs are saved into the `results/` directory, which is structured to separate native framework outputs from custom logs.

### `results/yolo_run/`
This directory contains the raw, unmodified output from the `ultralytics` YOLOv12 trainer. For each experiment run, you will find:
*   `weights/`: Directory containing the trained model checkpoints (`best.pt`, `last.pt`, and `epoch_XX.pt`).
*   `results.csv`: A log of metrics for each training epoch.
*   Training plots (e.g., `results.png`, `confusion_matrix.png`).
*   Validation image batches.

### `results/experiment_outputs/`
This directory contains custom, structured logs generated by our pipeline for easier analysis.
*   `final_run_config.yaml`: The exact YAML configuration generated from the AAS for this specific run, ensuring perfect reproducibility.
*   `periodic_test_evaluations/`:
    *   `evaluation_summary.csv`: A comprehensive CSV file containing the evaluation results (mAP, Precision, Recall) for every checkpoint saved during the `save_period`. This is the primary file for tracking model performance over time on the test set.
    *   `yolo_native_outputs/`: Raw YOLO output from the periodic evaluations.
*   `evaluation_summaries/` (Generated by `evaluate` mode):
    *   `all_evaluation_results.csv`: A master CSV logging the performance of all evaluated `.pt` files (best, last, etc.).
    *   Individual `.txt` summaries for each model evaluated, providing a human-readable report.
